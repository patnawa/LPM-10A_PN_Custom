# RX PN 1.5 follow-up review — 2026-09-19

**Follow-up:** the three corrections are implemented in the separate PN 1.6
candidate. See [implementation and validation](RX-FIXES-PN1.6-2026-09-19.md).
The report below records the original PN 1.5 findings and analysis scope.

PN 1.5 still has three reproducible behavioral defects worth fixing. Prioritize
sample ownership during mode changes, then stale data when a detection gate
reopens, then digital beep scheduling. The existing 28 tests pass; these
scenarios extend their coverage. No firmware patch or new binary was made.

Reviewed image: `experimental/APP_LPM-10RX_PN1.5-audit.bin`, 26,152 bytes,
SHA-256 `6874d65549e3c67b3ad1020495effc93645e325e104eaa7697737a44c11fb0cd`.
The review covers the actual patched instructions and inherited vendor code.
It does not assume that older audit findings remain unfixed in PN 1.5.

| Priority | Confirmed issue | Observable consequence in CPU reproduction |
|---|---|---|
| P2, fix first | Mode changes retain sampler indices and shared-buffer contents | Four new zero mains samples plus 60 old samples produce magnitude 437 and a 50 ms detection beep. |
| P2 | Closing the digital gate freezes a completed window; reopening consumes it | An old coded window triggers a new 800 ms signal hold without acquiring any fresh samples. |
| P2 | Every accepted digital window restarts beep and gap countdowns | Constant medium-strength input stretches some nominal 50 ms beeps to 92 timer ticks in the modeled schedule. |

P2 means a functional correction is warranted. These reproductions do not
establish a crash, permanent lockup, memory corruption, or frequency of occurrence
on a physical probe.

## 1. Reset sampler ownership when changing modes

The key handler at `0x080082B8` changes `mode` at `0x08008306`,
`0x08008346`, and `0x080083C6`, updates LEDs, and requests a confirmation
beep. It leaves all three sample indices, the digital sub-sample state,
`sampling_active`, shared sample data, and recent-detection state untouched.

All modes use the buffer at `0x2000006E`, but their sampling rates, window
lengths, and—in mains mode—ADC channels differ. TIM5 resumes the selected
mode's retained index. The main-loop analyzers do not check which mode produced
a completed window.

Reproduction seeds a reachable transition state: an earlier mains session was
interrupted with its index at 60, and analog mode subsequently filled the shared
buffer with 4095-count samples. Execute an accepted mains-key release, then the
actual TIM5 handler with channel 7 returning zero. It takes only four new samples
to complete the window. The actual mains analyzer and DFT report magnitude
**437**, above the strong threshold of 350, and request a **50 ms beep**.
The diagnostic clears the normal key-confirmation beep before analysis so it
cannot be mistaken for detection output.

This is a false indication from mixed sample histories. A second route exists:
changing modes while `sampling_active == 0` lets the new analyzer consume an
entire completed window from the previous mode. Digital and analog paths have
the same ownership problem; the mains reproduction is the concrete tested case.

**Proposed correction:** apply mode transitions at a safe analysis boundary,
briefly stop sampling, reset indices/sub-sample state and obsolete feedback,
then collect a complete window for the new mode. Merely clearing indices in the
key ISR is insufficient if an old analyzer is still executing and subsequently
publishes its result or rearms sampling. Use main-loop transition handling or
a generation check to reject work from the previous mode. Avoid masking interrupts
through a full DFT.

**Acceptance coverage:** all six directed mode transitions, partial and complete
windows, and changes during analysis. A detection after transition must derive
from a complete window belonging to the new mode.

## 2. Discard old data while a detection gate is closed

In [`rx_patches.py`](../LPM-10A/Firmware%20File/rx-sdk/rx_patches.py),
`p_digital_correlation` returns through `early_out` when `mode0_gate < 2`.
If a window is already complete, this leaves `sampling_active == 0`.
TIM5 consequently stops collecting new samples. When the gate later opens,
the detector immediately processes that old window.

The diagnostic loads a completed valid coded window, closes the gate, executes
100 detector/TIM5 pairs, and verifies that the buffer remains frozen. Reopening
the gate produces a **30 ms beep and an 800 ms recent-signal hold with zero new
samples**. The stale window can outlive the original signal; the firmware has
no freshness check. This issue is independent of mode changes.

The analog gate branch at `0x08009F7C` also returns without rearming, so its
control flow has the same stale-window pattern. The executable reproduction
here specifically covers digital mode. The physical meaning and operating
range of channel 3 are not confirmed, so how often the gate crosses these
thresholds on hardware remains unknown.

**Proposed correction:** discard completed windows while the gate is closed
and define reopening to require fresh acquisition. Account for a gate change
partway through a window, rather than simply analyzing the pending window as
soon as the threshold is crossed.

**Acceptance coverage:** collect a valid signal, close the gate, remove the
signal, reopen the gate, and confirm no replay. Separately verify reacquisition
of a signal that is still present.

## 3. Separate signal refresh from beep timing

The graded `detected` path in `p_digital_correlation` writes both
`beep_gap_ctr` and the active beep countdown on every accepted window.
`p_digital_strength` also runs a repeat scheduler. Therefore, fresh detections
restart that scheduler even when signal strength is constant.

The existing `test_strength_levels_and_repeat_cadence` checks a detection and
repeat timing separately. It does not continue feeding fresh detections during
the repeated beeps.

Using the actual detector, TIM1 countdowns, and digital repeat helper, with a
clean completed window every 240 nominal millisecond ticks:

| Grade | Declared on/off durations | Observed interference from fresh detections |
|---|---|---|
| Low | 50/100 ms | Beep starts at ticks 0, 149, 240, 389, 480: alternating 149/91-tick intervals. |
| Medium | 50/50 ms | Completed beep widths include 50, 50, 92, 50, 92 ticks. |
| High | 30/30 ms | Some 30-tick beeps extend to 34 ticks in this schedule. |

The one-tick offset in ordinary repeat intervals follows the existing countdown
ordering. The larger irregularities follow unconditional writes by the detector.
This is a deterministic timer model, not a cycle-accurate audio trace: the real
window is approximately 240 ms, the repeat helper runs more frequently than the
model's 1 ms observation interval, and interrupt delays can shift exact edges.
The conflicting countdown writes remain regardless of those timing details.

**Proposed correction:** let accepted windows update strength and signal expiry;
let one scheduler own on/off countdowns. Start a beep immediately for a newly
acquired signal, then apply strength changes at a defined phase boundary without
restarting an unchanged cadence.

**Acceptance coverage:** sustained detections over several seconds for all
grades, varying window arrival phase, changing grades, loss/reacquisition, and
key-confirmation feedback.

## Improvements needing measurement

- **ADC and interrupt timing:** the completion wait masks interrupts, and TIM1
  takes battery/channel-3 readings periodically. Measure worst-case transaction
  and handler durations against TIM5's roughly 25 microsecond period, plus
  sample spacing and speaker jitter. Current tests model conversion completion
  but do not establish real interrupt deadlines.
- **Digital strength calibration:** contrast thresholds are provisional and
  lack confirmed front-end gain normalization. Measure weak/strong signals,
  adjacent-cable pickup, noise, and gain changes before tuning them.
- **Sampling phase tolerance:** the current detector searches bit rotations
  and tolerates errors; it does not perform sub-slot clock recovery. Assess
  continuous recordings before committing to oversampling or a new sampler.

These are validation/design opportunities, not additional reproduced defects.


Results on this review: **28 existing tests passed; all three additional defect
reproductions succeeded**. The existing tests rebuild and compare the released
candidate. The diagnostic reads only the pinned PN 1.5 binary and refuses a
different hash; its assertions document known defective behavior rather than
desired post-fix behavior.

[`diagnose_pn15.py`](../LPM-10A/Firmware%20File/rx-sdk/diagnose_pn15.py) executes
actual key, sampling, analysis and timer code where described, while modeling
GPIO/ADC boundaries and scheduling. It does not flash a device or modify firmware.
The proposed fixes are not implemented. Their device validation would still be
required after instruction-level regression testing.
