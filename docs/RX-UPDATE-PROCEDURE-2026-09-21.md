# RX: วิธีอัปเดตเฟิร์มแวร์ที่ใช้ได้จริง และการพิสูจน์ (2026-09-21)

วันนี้หาสาเหตุที่ RX (probe) ไม่รับเฟิร์มแวร์ได้สำเร็จ โดยต่อ ST-Link V2 อ่าน SRAM ของ
บูตโหลดเดอร์แบบอ่านอย่างเดียว (ไม่มี halt/reset/เขียน flash/เปลี่ยน option bytes) ขณะก๊อปปี้
ไฟล์เข้าไดรฟ์ `BOOTLOADER` ทีละแบบ ผลลัพธ์: **RX PN 1.12 ถูกติดตั้งและทำงานบนเครื่องจริง**
และเจ้าของเครื่องรายงานว่า "ดีเลย์ Digital 1 วินาทีหายแล้ว จังหวะละเอียดขึ้นกว่าเฟิร์มแวร์โรงงาน"

## ข้อสรุป

| สิ่งที่ก๊อปปี้เข้าไดรฟ์ | ไฟล์สถานะบนไดรฟ์ | ผล |
|---|---|---|
| image ดิบ (`APP_LPM-10RX_*.bin` ของ FNIRSI, PN ทุกตัวก่อนหน้า) ไม่ว่าชื่อใด | `UNKOWN.TXT` | รับข้อมูลครบทุก sector แล้วทิ้ง ไม่เขียน flash |
| container (หัว 4 KB + image) เขียน**ช้า** ทีละ sector เว้น 0.3–0.5 s | `APPRUN.TXT` | เห็นหัวแล้ว 150 ms ต่อมาปิด USB กระโดดเข้าแอปเดิม ไม่เขียน |
| container เขียนแบบ unbuffered รวดเดียว (custom writer) | `UNKOWN.TXT` | ไม่เขียน |
| **container ก๊อปปี้แบบปกติ (Explorer / `Copy-Item`)** | (ไดรฟ์หายทันที) | **เขียนเสร็จใน ~1 s แล้วรีบูตเข้าแอปใหม่**; เข้า UDISK ครั้งถัดไปแสดง `<เวอร์ชัน>.TXT` เช่น `3.0.2.TXT` |

รูปแบบ container = แบบเดียวกับไฟล์ TX ของ FNIRSI (`LPM-10A-TX_V2.0.7_260610.bin`):

```
0x0000  char name[32]   เช่น "APP_LPM-10RX_V3.0.0_260416.bin" (ชื่อ/เวอร์ชันในหัวไม่มีผลต่อการรับ)
0x0020  u32  payload_off = 0x1000
0x0024  u32  payload_len = ขนาด image ดิบ (26152)
0x0028  u32  payload_end = 0x1000 + payload_len - 1
0x002C  ศูนย์จนถึง 0x1000
0x1000  image ดิบ (โหลดที่ 0x08006800)
        เติมศูนย์ให้เป็นผลคูณ 4 KB (ไฟล์ 32768 ไบต์)
```

ไฟล์ RX ในแพ็กเกจ FNIRSI V2.0.7 เป็น image ดิบ จึงใช้อัปเดตผ่านไดรฟ์ไม่ได้ตรง ๆ — ไม่ใช่เพราะ
เวอร์ชัน ไม่ใช่เพราะกันดาวน์เกรด และไม่ใช่เพราะการแก้ของ PN

`rx-sdk/build.py --write` ตอนนี้ออกไฟล์ `<ชื่อ>-update.bin` (ห่อด้วย `lpm10rx/container.py`) ควบคู่กับ
image ดิบทุกครั้ง **ก๊อปปี้ไฟล์ `-update.bin` เท่านั้น** ด้วย Explorer ห้ามใช้ตัวเขียนที่หน่วงเวลา

## ขั้นตอนอัปเดต / ย้อนกลับ

1. ปิด RX → กด SCAN ค้าง → เสียบ USB → ไดรฟ์ `BOOTLOADER` ขึ้น (ไฟล์เปล่า `<สถานะ>.TXT` คือช่องบอกสถานะ
   ของบูตโหลดเดอร์ Windows อาจแสดงชื่อเก่าจาก cache; ชื่อจริงเห็นตอน mount ใหม่)
2. ก๊อปปี้ `*-update.bin` ด้วย Explorer หนึ่งไฟล์ ภายใน ~1 s ไดรฟ์จะหายและ RX รีบูตเข้าแอปใหม่เอง
3. ถอด USB ใช้งานได้เลย ถ้าเครื่องรอปุ่ม ให้กดเปิดตามปกติ

ย้อนกลับ: ก๊อปปี้ container ของ image โรงงาน V3.0.0 ด้วยวิธีเดียวกัน (พิสูจน์แล้ว 2026-09-21 12:33 ว่า
ติดตั้งได้) ไฟล์โรงงานไม่อยู่ใน repo ให้สร้างจาก `APP_LPM-10RX_V3.0.0_260416.bin` ด้วย
`python -c "from lpm10rx.container import wrap; ..."` หรือ build โดยไม่เลือก patch เวอร์ชัน 3.0.1 ที่เครื่อง
เคยมี **ไม่มีไฟล์ กลับไปไม่ได้**

## หลักฐานว่าเขียนจริง (อ่านจาก SRAM ผ่าน SWD, โฟลเดอร์ `Desktop/LPM-10RX-SWD-2026-09-21/`)

- ก่อนวันนี้ RAM ของแอปมี layout ต่างจาก V3.0.0 (index ที่ `0x5D`, ตัวนับปุ่ม `0xD6/0xDA/0xE2`,
  return address `0x0800BAD1` ไม่ใช่จุด BL ใน V3.0.0) → เฟิร์มแวร์เดิมเป็นคนละบิลด์ (น่าจะ 3.0.1)
  **ดังนั้นผล "device test pass" ของ RX PN 1.3–1.8 ที่รายงานก่อนหน้าคือการทดสอบเฟิร์มแวร์โรงงานตัวนั้น**
- หลังก๊อปปี้ container V3.0.0 (สตริง 3.0.2): layout ตรง static RE ของ V3.0.0 (index `0x5B`, substep `0xEE`),
  return address `0x0800B911`/`0x0800ACD1` เป็นจุด BL ใน V3.0.0; UDISK รอบถัดไปแสดง `3.0.2.TXT`
- หลังก๊อปปี้ `APP_LPM-10RX_PN1.12-overload-update.bin` (12:40): return address ทั้งสี่
  (`0x0800AC63`, `0x08009E11`, `0x0800837F`, `0x0800B8F7`) เป็นจุด BL **เฉพาะใน PN 1.12** และอยู่ในช่วง
  โค้ดที่ PN แก้; RAM มี gate byte `0x200000EF` และฟิลด์ `0xEC` ของ PN
- ระหว่างรับไฟล์: sector buffer 2 KB ที่ `0x20000354`, LBA ที่ `0x20000128`, ตัวนับข้อมูลรับ `0x20000095`
  (+8 ต่อ sector, หน่วย 256 ไบต์), directory entry ตัวแรกที่ `0x2000025C`, ชื่อไฟล์สถานะ `0x20000050`

## เครื่องมือ (อ่านอย่างเดียว) ใน `docs/experiments/`

- `rx_ro.py status|sram|watch` — DBG_ID/VTOR/FLASH_OB, snapshot SRAM 24 KB, diff ต่อเนื่อง
- `rx_trigwatch.py` — เฝ้า 1 KB แรก + VTOR ทุก ~150 ms ทนสายหลุด (ใช้จับจังหวะบูตโหลดเดอร์)
- `rx_fastwatch.py` — เฝ้าช่วงที่กำหนดเร็วที่สุด
- `rx_slow_copy.py` — ตัวเขียนทีละ sector ที่ใช้พิสูจน์ว่าการเขียนช้าทำให้บูตโหลดเดอร์ยอมแพ้ (`APPRUN`)

ต้องใช้ pyOCD 0.45.1 ใน venv, ST-Link driver STSW-LINK009; เปิด RX ด้วยแบตก่อน แล้วต่อเฉพาะ
GND/SWCLK/SWDIO ชิปยังล็อก L1 อยู่ — **ห้าม unlock / mass erase** (จะลบบูตโหลดเดอร์และ licence block)

## สิ่งที่ยังไม่รู้

- เงื่อนไขที่บูตโหลดเดอร์ใช้แยก "เขียนปกติ" กับ "เขียนช้า/สตรีม" (น่าจะเป็น idle timeout ราว 100 ms
  หรือลำดับ directory-entry/FAT ที่ Windows เขียน) — รู้แค่ว่า Explorer ใช้ได้เสมอ (3/3 ครั้ง)
- ความหมายตรงของสถานะ `UNKOWN`/`APPRUN` นอกจากที่สังเกต; ไม่พบ checksum ใน container
