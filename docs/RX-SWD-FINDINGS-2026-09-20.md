# RX: ผลตรวจ SWD และ reverse engineering จากเครื่องจริง

วันที่ 2026-09-20. ผู้ใช้ต่อโปรแกรมเมอร์และอนุญาตให้ตรวจ จากนั้นขอให้ทำ
reverse engineering ต่อเต็มที่ งานนี้ยังไม่ได้สำรอง main flash หรือแก้อาการ
Digital ด้วยเฟิร์มแวร์ใหม่ แต่ได้ข้อมูลตัวชิปและพฤติกรรมจริงเพิ่มจากการทดสอบ UDISK

**ข้อค้นพบหลัก:** ข้อมูลขณะรับ Digital ไม่ตรงกับการทำงานปกติของ PN 1.13
ที่สร้างไว้ แอปจริงยังเริ่มบี๊บซ้ำระหว่างเก็บผลตรวจพบไว้ประมาณ 800 ticks
การแก้ขั้นต่อไปจึงต้องใช้ไฟล์ RX ที่ตรงกับเครื่องและเส้นทางอัปเดตที่ยืนยันได้
ก่อนผูกผลทดสอบกับเฟิร์มแวร์ PN ยังยืนยันชื่อเวอร์ชันจริงไม่ได้

## การเชื่อมต่อและตัวชิป

Windows พบ `USB VID_0483 / PID_3748` เป็น **ST-Link V2**; ผู้ใช้ยืนยันชื่อ
อุปกรณ์อีกครั้ง ไม่ใช่ J-Link ที่กล่าวตอนแรก เริ่มต้นไดรเวอร์ขาด (Code 28)
จึงติดตั้ง `stlink_dbg_winusb.inf` จากแพ็กเกจ STSW-LINK009 ที่มีอยู่ใน Downloads
ตรวจลายเซ็น catalog ก่อนติดตั้ง และตรวจการติดต่อจริงหลังสถานะเปลี่ยนเป็น Code 0
ติดตั้ง pyOCD 0.45.1 และ libusb-package ใน virtual environment แยกสำหรับงานนี้
โดยไม่ได้อัปเดตเฟิร์มแวร์ของ ST-Link

| สิ่งที่อ่านได้ | ผล |
|---|---|
| ST-Link firmware | `V2J31M7` |
| แรงดันที่โปรแกรมเมอร์รายงาน | ประมาณ 3.15 V; ไม่ใช่ผลวัดด้วยมัลติมิเตอร์ที่จุดจ่ายไฟ RX |
| SWD DPIDR | `0x2BA01477` |
| Cortex-M CPUID | `0x410FC241` |
| Nations DBG_ID | `0x22644017`: **N32L406, flash 128 KiB, SRAM 24 KiB, revision 0x17** |
| FLASH_OB | `0x03FFFFFE`: L1 เปิด, L2 ปิด, OBERR=0 |
| RDP1 / complement | `00 / FF` |
| VTOR | `0x08006800` ซึ่งตรงฐานแอปที่คาดไว้; ไม่ยืนยันเลขรุ่นเฟิร์มแวร์ |

ผู้ใช้แจ้งว่าตัวอักษรบน MCU ถูกลบ การระบุรุ่นข้างต้นมาจากรีจิสเตอร์
ไม่ใช่การเดาจากรูปหรือ USB descriptor ดู [หลักฐานการอ่านตัวชิป](experiments/results/rx-swd-chip-identity-2026-09-20.json)
และ [คู่มือ/การแปลสถานะ L1](RX-SWD-PROTECTION-REFERENCE-2026-09-20.md)

อ่าน flash ที่ `0x08000000`, `0x08006800` และ `0x0801F000` เกิด transfer fault
ขณะที่ CPUID อ่านซ้ำได้และ SRAM อ่านได้ สอดคล้องกับ L1 การเปลี่ยน L1 เป็น L0
จะลบ main flash จึงไม่ได้ทำ Unlock, Recover, mass erase หรือเปลี่ยน option bytes
ไม่มี full flash backup และยังไม่รู้ hash ของแอปในเครื่อง

## สภาพจ่ายไฟมีผลต่อการตรวจ

การต่อครั้งแรกทำให้ CPU ประมวลผล แต่ TIM1/TIM5 ยังไม่เริ่มและตัวนับใน RAM เป็นศูนย์
`DHCSR=0x01010000` หลายครั้ง: มี instruction retirement, ไม่ halt/lockup,
และ C_DEBUGEN=0 ต่อมาอ่าน ICSR/CFSR/HFSR/DFSR เป็นศูนย์
ข้อมูลนี้ไม่ใช่หลักฐานว่าแอปกำลังรับสัญญาณตามปกติ

ผู้ใช้ต่อแบตแล้วเปิด RX ไม่ได้ขณะต่อ ST-Link แต่เมื่อถอด ST-Link ทุกเส้น
เปิดด้วยแบตได้ตามปกติ จากนั้นเปิด RX ด้วยแบตก่อน แล้วต่อเฉพาะ GND/SWCLK/SWDIO
โดยเว้นสาย 3.3 V/5 V และสายอื่น จึงเปิดใช้งานพร้อมอ่าน SWD ได้
สาเหตุทางไฟฟ้าหรือ branch ที่เครื่องเข้าตอนแรกยังไม่ได้พิสูจน์
การเริ่มต้นจ่ายไฟและ startup polling เป็นคำอธิบายที่ต้องแยกจากเฟิร์มแวร์เสีย
ดู [การไล่ startup ในไฟล์เดิม](RX-UPDATE-STATIC-RE-2026-09-20.md)

รูปบอร์ดที่ตรวจด้วยสายตาคือ `99035_0.jpg` ถึง `99038_0.jpg` ใน
`C:/Users/Alpha/Desktop/RX`. เห็นบอร์ดสองด้าน, MCU แบบมีขารอบตัว,
หัวต่อ debug สี่จุด, USB-C, ปุ่มและวงจรขยายสัญญาณ แต่ภาพไม่ได้ยืนยันเบอร์
ชิปย่อยทั้งหมด, ความถี่คริสตัล, netlist หรือชื่อขาที่มองไม่ชัด
การต่อ SWD ได้จริงเป็นหลักฐานการเชื่อมต่อที่หนักแน่นกว่าการเดาสีสายจากภาพ

`digital-pause-20260920-221932.jsonl` พร้อม metadata ข้างกันในโฟลเดอร์ Desktop เดียวกัน
ตำแหน่งที่อ่านและ raw bytes ถูกเก็บไว้ เพื่อแปลใหม่ได้เมื่อพบว่าตำแหน่งตัวแปร
ในเครื่องต่างจากไฟล์ที่มีอยู่ ห้ามใช้ชื่อ field ที่ตั้งตาม V3.0.0 ในไฟล์บันทึกครั้งแรก
เป็นหลักฐานยืนยัน layout โดยไม่ตรวจ raw bytes

ผล [วิเคราะห์ Digital จากข้อมูลจริง](RX-LIVE-DIGITAL-RELEASE-2026-09-20.md)
พบ GAP ที่ `0x2000005C`, Digital index ที่ `0x2000005D` และ RECENT ที่
`0x2000006E` ต่างจากไฟล์ฐานเดิมสองไบต์ ความสัมพันธ์ของ sensitivity samples,
trimmed mean และการหาร 580 ตรงกันครบ 2,348 ชุด จึงไม่ใช่แค่เดาจากค่าตัวเดียว
หลัง RECENT ถูกเติมครั้งสุดท้าย ยังเริ่มเสียงใหม่อีกแปดครั้ง จน BEEP เป็นศูนย์
ประมาณ **0.816–0.865 วินาทีหลังการตรวจพบครั้งสุดท้าย**
ช่วงนี้เป็นเวลาระหว่างข้อมูลใน RX ไม่ใช่เวลาจากปุ่ม Pause ที่วัดตรงจาก TX
TIM1/TIM5 เดินปกติระหว่างการบันทึก เสียงตามหลังที่เห็นมาจากการเริ่มเสียงซ้ำ
ขณะเก็บผลตรวจพบไว้ประมาณ 800 ticks

ตรวจเทียบคำสั่งจริงใน RX ทั้ง 16 ไฟล์แล้ว: PN 1.13 ต้องมี gate byte ที่
`0x200000EF=2` และ RECENT ที่ `0x2000006C>500` เพื่อเริ่มเสียง Digital
แต่ข้อมูลจริงที่สองตำแหน่งนี้เป็น 0 และ 2 ตลอดทุกชุด จึงไม่ตรงกับการทำงาน
ปกติของ PN 1.13 ที่สร้างไว้ ดู [หลักฐาน static และ hashes](experiments/results/rx-live-abi-comparison-2026-09-20.json)

อ่านเฉพาะ DBG_ID/VTOR และช่วง SRAM ที่กำหนด ตรวจ chip ID และ probe ID ก่อนเริ่ม
ไม่มี target definition, flash algorithm, user script, คำสั่ง halt/reset หรือ target-memory write
การเปิด SWD และล้าง sticky fault ของ transport ยังมี debug-port register writes
จึงเรียกงานนี้ว่าการอ่านโดยไม่เขียน flash/option bytes ไม่ใช่ไม่มีการเขียนใด ๆ บนบัส

## ขอบเขตของข้อสรุป

ตรวจ UDISK เพิ่มด้วย RAM ของบูตโหลดเดอร์, raw read แบบ FILE_FLAG_NO_BUFFERING
และ SCSI READ(10) โดยตรง ทั้งหมดให้ชื่อ `UNKOWN.TXT` ตรงกัน
จากนั้นอ่านครบ **51,200 เซกเตอร์ × 2,048 bytes = 100 MiB** โดยไม่เกิด SCSI error
พบข้อมูลไม่เป็นศูนย์เพียง 93 bytes ที่ LBA 0, 2, 27, 28 ซึ่งเป็น metadata
พื้นที่ data ทั้งหมดเป็นศูนย์ จึงไม่พบภาพเฟิร์มแวร์ผ่านการอ่านไดรฟ์ในสถานะนี้
ผลนี้ไม่ได้ตัดความเป็นไปได้ของคำสั่งหรือสถานะอื่นที่ยังไม่ทราบ

BPB ประกาศ FAT2 เริ่มที่ LBA 15 แต่ reserved-entry bytes กลับปรากฏที่ LBA 27
FAT สองชุดต่างกันแปดไบต์ และ boot sector ที่คืนมาไม่มี `55 AA` ที่ offset 510
ข้อผิดปกติเหล่านี้ตรวจซ้ำจากไฟล์ผลอ่านได้ แต่ยังไม่พิสูจน์ว่าเป็นสาเหตุปฏิเสธ
เฟิร์มแวร์ ห้ามแก้ FAT/format/write raw sectors เพื่อเดาการแก้ไข
ดู [รายงาน UDISK/RAM](RX-UDISK-RAM-RE-2026-09-20.md) และ
[ผลอ่านครบพื้นที่](experiments/results/rx-udisk-complete-read-scan-2026-09-20.json)

ตรวจ [แพ็กเกจทางการสี่ชุด](RX-OFFICIAL-IMAGE-SEARCH-2026-09-20.md) แล้ว
ยังพบ RX เพียง `APP_LPM-10RX_V3.0.0_260416.bin` เดิม ไม่มีไฟล์ RX อีกชุด
สำหรับเทียบ layout นี้ และแพ็กเกจไม่ได้ให้ bootloader RX
ยังไม่มีวิธีอ่าน main flash โดยไม่ลบที่ยืนยันว่าใช้ได้กับ N32L406 เครื่องนี้

ฐานแอปและ clocks ตรงกันไม่ได้แปลว่าไฟล์ PN ถูกติดตั้งแล้ว
ตัวแปรระหว่างการรับ Digital แสดง layout ต่างจากฐาน V3.0.0 ที่ใช้สร้าง PN
จึงต้องตรวจแอปที่รันอยู่ก่อนแก้ binary เพิ่ม ผลนี้ไม่ยืนยันเลขรุ่น 3.0.1
และยังไม่อธิบายเงื่อนไขที่บูตโหลดเดอร์ยอมรับหรือปฏิเสธไฟล์

งานตรวจทั้งหมดในรอบ SWD นี้ไม่ได้เขียนเฟิร์มแวร์หรือ option bytes,
ไม่ได้สั่ง halt/reset และไม่ได้ทำลายข้อมูลในเครื่อง ผู้ใช้ยืนยันการเปิดตามปกติ
หลังถอดโปรแกรมเมอร์ และการเปิดด้วยแบตพร้อมต่อสัญญาณสามสายสำเร็จแล้ว
หลังจบการอ่าน UDISK ทั้งหมด ผู้ใช้ถอด USB/SWD แล้วตอบยืนยันอีกครั้งว่า
**“RX เปิดและทำงานได้ปกติ”**
