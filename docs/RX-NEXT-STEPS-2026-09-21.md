### ทำไมไม่ทำ matched filter (ตัวเลขจาก window จริง 7,992 ชุดของวันนี้ — `docs/experiments/rx_matched_filter_model.py`)

- รหัส `0xB6B6` ที่ TX ส่งมีคาบจริงแค่ **8 chip** (`10110110` ซ้ำ) และไม่สมดุล (5 ต่อ 3) → correlation ของ phase อื่นสูงตาม
  margin ระหว่าง phase ที่ดีสุดกับ phase อื่นอยู่แค่ ~2 ทั้งสัญญาณจริงและ noise → ใช้แยกไม่ได้
- ใช้ normalized correlation (ρ) แทน: window ที่ PN รับได้ ρ มัธยฐาน 0.88 แต่ **noise (ไม่มีสัญญาณ, p-p ≤ 40) มี ρ ถึง 0.77 ที่ p95**
  เพราะ noise ไม่ขาว — ฮัม 50 Hz = คาบ 4 sample ซ้อนกับคาบ 8 ของรหัสพอดี → false alarm 8–20 % ที่เกณฑ์ที่ยังรับสัญญาณจริงได้ 70–83 %
- ที่สัญญาณอ่อน (p-p 30–60) ตัวตรวจจับ PN ล็อกได้ 45 % ส่วน ρ ≥ 0.5 ได้ 63 % — ต่างกันน้อย และที่ p-p > 60 PN ล็อกได้ 77–99 % อยู่แล้ว
- สัญญาณจริงเป็น on/off ชัด (chip ปิด = 0 count) การตัดสินทีละบิตจึงเหมาะกับรูปสัญญาณนี้อยู่แล้ว
สรุป: ความไวถูกจำกัดด้วยเกนแอนะล็อกและ noise ฮัม ไม่ใช่วิธีตัดสิน → AGC (ข้อ 2) คือคันโยกที่ถูก ถ้าจะขยับต่อจริงคือ
**notch 50/60 Hz ก่อนตัดสิน** (ลบค่าเฉลี่ยเคลื่อนที่ 4 sample) ซึ่งเป็นงานเล็กและวัดผลได้ด้วยชุด jsonl เดิม

## 1. ไฟล์สถานะบนไดรฟ์บอกรุ่น PN (แนะนำทำก่อน)

**ปัจจุบัน** PN ทุกรุ่นคงสตริง `3.0.0` (ที่ `0x0800CDE4`, ช่อง 8 ไบต์) แอปเขียนสตริงนี้ลง version page `0x0801F000`
ตอนบูตเมื่อไม่ตรง และบูตโหลดเดอร์เอาไปตั้งชื่อไฟล์สถานะ (`3.0.0.TXT`) จึงแยกรุ่น PN จากไดรฟ์ไม่ได้
**ทำ**: เปลี่ยนเป็น `PN1.19` (6 ตัวอักษร + NUL พอดีช่อง) → ไดรฟ์แสดง `PN1.19.TXT`
**ตรวจแล้ว**: โค้ด `version_page_check` ใช้ `strlen` ไม่ผูกความยาว; บูตโหลดเดอร์ไม่เช็กหน้านี้ตอนรับไฟล์
(วันนี้แฟลชผ่านทั้งตอนหน้าเป็น 3.0.2 และ 3.0.0); tag `_V3.` ที่บูตโหลดเดอร์ตรวจอยู่คนละหน้า (`0x0800676E`) ไม่แตะ
**ความเสี่ยงที่เหลือ**: ชื่อไฟล์ 8.3 — `PN1.19` มีจุด 1 จุดเหมือน `3.0.0` ที่ใช้ได้อยู่แล้ว; ถ้าบูตโหลดเดอร์ตัดชื่อแปลก ๆ
จะเห็นแค่ชื่อเพี้ยน ไม่กระทบการทำงาน

## 2. AGC ลดเกนอัตโนมัติเมื่อภาคขยายอิ่ม

**หลักฐาน**: ที่ code 4–7 p-p ไม่เกิน ~2000–2600 ไม่ว่าแนบสายแค่ไหน (ภาคขยายอิ่มก่อน ADC) → ที่ปุ่มสูงทุกสายที่ใกล้จะ
"เร็วสุด" เท่ากันหมด แยกไม่ออกจนกว่าจะหมุนปุ่มลง และ Analog ที่อิ่มเคยหลุดล็อกเป็นช่วง (DFT margin พังเพราะคลิป)
**ทำ**: ใน `gain_select_3bit` (ที่ PN 1.17 hook อยู่แล้ว) ถ้า window ล่าสุดอิ่ม (เช่น ≥ 8/64 sample ที่ ≥ 4000 หรือ p-p > 2300)
ให้ใช้ level ต่ำลง 1 ขั้นชั่วคราว (4–7 → 2, 2 → 1) และ**ปรับตัวคูณ normalizer ตาม level ที่ใช้จริง** (ตอนนี้ normalizer อ่าน
`0x6A` = level จากปุ่ม ต้องเปลี่ยนให้อ่าน level ที่ใช้จริง) ต้องมี hysteresis: ถอยขึ้นเมื่อ p-p < ~600 ต่อเนื่อง ≥ 1 s
**ต้องการ RAM**: 1 ไบต์ (level ที่ใช้จริง) + 1 ไบต์ตัวนับ — ต้องหาไบต์ padding ที่ยังว่าง (PN 1.6 ใช้ `0x49`, `0xEF` ไปแล้ว;
ตรวจด้วย `rx-sdk` ว่า `0x2000005E–0x5F`, `0x200000EC`, `0x200000F1–0xF3` ว่างจริง — `0x5E/0x5F` มีค่าใน capture วันนี้ อาจไม่ว่าง)
**ทดสอบ**: unicorn ป้อนลำดับ p-p อิ่ม/ไม่อิ่ม ดูการสลับ level และค่าที่ normalizer ใช้; บนเครื่อง: capture `0x6A` และ level จริง
ขณะแนบสายที่ปุ่มสุด ต้องเห็น level ลดและ p-p กลับมาช่วง 800–1900
**ผลข้างเคียงที่ต้องดู**: gate ของโหมด (Digital raw ≥ 2 / Analog code ≥ 1) ใช้ค่าจากปุ่ม ไม่ใช่ level จริง — ดีอยู่แล้ว

## 3. Digital อัปเดตทุก 8 samples (40 ms) แทน 16 (80 ms)

**หลักฐาน**: Digital รีเฟรช ~9 ครั้ง/วิ (วัดจาก RECENT) เทียบ Analog ~48 ครั้ง/วิ; เจ้าของรู้สึกว่า Analog ตอบสนองดีกว่า
**ทำ**: ใน `digital_tracking` (PN 1.11) หน้าต่าง 48 samples เก็บ 32 เดิม + รับใหม่ 16 → เปลี่ยนเป็นเก็บ 40 + รับใหม่ 8
ตัวนับ index/ownership ใน `sampling_fixes` ต้องตามไปด้วย; strength จาก "16 samples ล่าสุดที่ผ่านรหัส" ยังใช้ได้ (ซ้อนกัน)
**ต้นทุน CPU**: correlation 48 บิต × 8 rotation ทุก 40 ms — ไม่กี่พันคำสั่ง ไม่มีปัญหา (Analog DFT ใช้ ~60k คำสั่งทุก 21 ms อยู่แล้ว)
**ทดสอบ**: มีคลัง window 2,490 ชุดและเทส "continuous windows" ของ PN 1.11 ปรับให้รับ stride 8; วัดบนเครื่องด้วย capture เดิม
(RECENT refresh/วิ ควรเป็น ~18)
**ข้อจำกัดที่ยังอยู่**: ล็อกครั้งแรกยังต้องรอ 48 samples = 240 ms (โค้ดซ้ำทุก 80 ms; อาจลดเป็น 32 samples = 160 ms ถ้ายอมรับ
false alarm สูงขึ้นเล็กน้อย — ควรทำหลังข้อ 4)

## 4. Digital matched filter (ตัวตรวจจับใหม่)

**หลักฐาน**: Digital ตัดสินทีละบิตด้วย threshold แล้วเทียบรหัส (ยอมผิด ≤ 4 บิต) — สัญญาณอ่อน/noise ทำให้บิตผิดก่อนที่
Analog (DFT รวมพลังงาน 64 จุด) จะพลาด; วันนี้ Digital หลุดล็อกที่ p-p ต่ำกว่า ~100 count ขณะ Analog ยังจับที่ p-p ใกล้เคียง
**ทำ**: correlate ค่า ADC ตรง ๆ (ลบ mean) กับรูปคลื่นรหัส ±1 ทั้ง 16 phase: S(φ)=Σ s_i·c_{(i+φ) mod 16} ใน 48 samples
→ เลือก |S| สูงสุด, margin = S_max / median|S(φ อื่น)| แบบเดียวกับ Analog (bin 17 เทียบ bin อื่น) → รับเมื่อ margin ≥ เกณฑ์
และ S_max เป็นคะแนนความแรงโดยตรง (เชิงเส้นกับแอมพลิจูด → ผ่าน normalizer/โค้งเดิมได้)
**ผลที่คาด**: processing gain ≈ 10·log10(48) ≈ 17 dB เทียบการตัดสินทีละบิต; ไม่ต้องมี contrast floor 192 อีก
**ต้นทุน**: 48×16 = 768 MAC ต่อ window + median 16 ค่า — เล็ก
**ความเสี่ยง**: false alarm จาก noise ที่บังเอิญ correlate; ต้องรันคลัง 49,152 synthetic noise windows ของ PN 1.11 เทียบ
อัตราเดิม (1 ครั้ง) และเทียบ 2,490 window จริง; ตั้งเกณฑ์ margin จากข้อมูลจริงที่ capture ได้ (มีไฟล์ sens-*.jsonl แล้ว
ใช้ทดสอบ offline ได้ทันทีก่อนเขียน assembly)
**ขั้นตอนที่แนะนำ**: (ก) เขียน Python model + รันกับ jsonl วันนี้ → ดู margin ของสัญญาณจริงเทียบ noise (ข) ตั้งเกณฑ์
(ค) เขียน assembly ลงพื้นที่ต่อท้าย image (มีที่เหลือ ~70 KB) (ง) unicorn เทียบ Python model ทุก window (จ) แฟลช + capture
**ทางเลือกที่เบากว่า**: คงตัวตรวจจับเดิม แต่ใช้ matched filter เฉพาะ "คะแนนความแรง" (แทน group medians) — ได้จังหวะที่นิ่ง
กว่าโดยไม่แตะเรื่อง false alarm

## 5. โปรโตคอลวัดภาคสนาม (ไม่ต้องเขียนโค้ด)

มี `TONE-PROBE-COMPARISON-PROTOCOL.md` อยู่แล้ว ปรับให้ใช้กับ PN 1.19: (1) ระยะจับสูงสุดต่อโหมดที่ปุ่มกลาง
(2) มัดสาย 4 เส้น ห่าง 1–2 cm: เลือกเส้นถูกกี่ครั้งใน 10 (3) crosstalk: จังหวะที่เส้นข้าง ๆ เทียบเส้นจริง (4) เวลาจากยก
probe ถึงเงียบ ทำทั้งก่อน/หลังข้อ 2–4 เพื่อให้ตัดสินใจจากตัวเลข ใช้ capture ผ่าน SWD ควบคู่ได้ (ค่า gap ที่ publish)

## 6. รวม profile chain ใน `build.py`

ตอนนี้ PN 1.19 = `--overload → --mode-tone → --gain-norm → --release-hold → --smooth-gain → --rail-strong → --strong-cap`
แต่ละอันมี guard ยาวใน build.py และ pin parent sha ต่อกันเป็นโซ่ — เพิ่มรุ่นใหม่ต้องแก้ 7 จุด
**ทำ**: ตาราง `PROFILES = {"pn1.19": [...patch ids...]}` + `--profile pn1.19`; เก็บ flag เดิมเป็น alias; verify.py ของ RX
ยังไม่รู้จัก image ที่ยาวขึ้น/container → เพิ่ม section "container + extension" ให้ตรวจ `-update.bin` ด้วย

## 7. Mains mode (50/60 Hz)

ยังใช้เสียงโรงงาน (บี๊บยาวตามระดับ ผ่าน keep_alive) และเสียง 2.5 kHz เท่า Digital — ใช้งานได้ ถ้าต้องการให้เป็นระบบเดียวกัน:
ให้ magnitude ของ bin 5/6 ผ่านโค้ง/normalizer เดียวกัน และเสียงต่ำสุด (เช่น 833 Hz = สลับทุก 24 tick ต้องใช้ modulo แทน mask)
ต้นทุนต่ำ ประโยชน์เฉพาะคนที่ใช้โหมดนี้

## TX — สิ่งที่ยังค้าง (ไม่เร่ง)

- **PoE กับแหล่งจ่ายจริง** ยังไม่เคยทดสอบ (ไม่มี PoE switch/injector) — เส้นทาง "Detecting → แรงดัน" ยืนยันด้วย emulation เท่านั้น
- **สายสั้นกว่า 2 m**: ข้อจำกัด PHY; build ทดลอง blind-zone 0.5 m มีไว้เก็บข้อมูล ยังไม่มีข้อมูลพอสรุป
- **Sync32**: ผลทดสอบเดิมใช้ไม่ได้ (RX เป็นโรงงาน) แต่ RX PN ปัจจุบันไม่มีตัวถอด และการจำลองไม่ชี้ว่าคุ้ม — ค่อยพิจารณาหลังข้อ 4
  ถ้า noise เป็นตัวจำกัดจริง; **Pulse test** ไม่ต้องนำกลับ
- Length/NVP/Zero, FLASH, แบต, Thai UI: ผ่านการทดสอบจริงแล้ว ไม่มีงานค้าง

## สิ่งที่ไม่ควรทำ

- ปลดล็อก/mass erase RX ผ่าน ST-Link (ลบบูตโหลดเดอร์และ licence block — กู้ไม่ได้)

- ยกเลิก hold/smoothing เพื่อให้ "ไวขึ้น" — จะกลับไปกระตุกตามข้อมูลวันนี้
