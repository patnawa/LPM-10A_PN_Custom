# RX: ขอบเขตการอ่านผ่าน SWD เมื่อเปิด L1

วันที่ตรวจ: 2026-09-20. เอกสารนี้สรุปข้อกำหนดชิป ไม่ใช่ผลสำรองแฟลชหรือหลักฐานว่าเฟิร์มแวร์ที่ส่งลง RX ถูกใช้งานแล้ว ไม่มีการสั่งฮาร์ดแวร์จากงานตรวจเอกสารนี้

แหล่งหลัก: [N32L40x Series User Manual](https://www.nsing.com.sg/uploads/MCUProducts/N32L40x/Chip_Documentation/User_Manual/EN_UM_N32L40x_Series_User_Manual.pdf), ไฟล์ 677 หน้า, SHA-256 `c80d1af55650bef408f9a655346f188e5777814810ad2afede9d07d47aa1eec5`. เลขหน้าอ้างอิงด้านล่างเป็นเลขที่พิมพ์ในเนื้อหา; หน้า PDF = เลขดังกล่าว + 25. ตรวจภาพตาราง 2-6 หน้า 16-19 แล้ว เพื่อแยกคอลัมน์ผู้เข้าถึงออกจากโหมดบูต

## สิทธิ์ L1 ที่เกี่ยวกับการตรวจเครื่อง

| รายการ | ขอบเขตที่คู่มือระบุ | หน้า / หัวข้อ |
|---|---|---|
| แฟลชโปรแกรมผ่าน JTAG/SWD | ห้ามอ่าน, program และ page erase ทั้งเมื่อบูตจาก main flash, SRAM และ system memory; mass erase เป็นรายการแยกที่อนุญาต แต่ลบข้อมูลเดิม | 15-19, 2.2.1.9 / ตาราง 2-6 |
| SRAM ผ่าน JTAG/SWD | ยังเข้าถึงได้; สิทธิ์นี้ไม่ได้ทำให้แฟลชอ่านได้ | 16-19, ตาราง 2-6 |
| Option bytes | ยังเข้าถึงได้ใน L1; การตรวจครั้งนี้ใช้การอ่านเท่านั้น | 16-19, ตาราง 2-6 |
| System memory / ROM ผ่าน JTAG/SWD | ตารางระบุห้ามเข้าถึง; ไม่ควรเหมารวมกับ system configuration ที่เก็บ UID | 16-19, ตาราง 2-6; 650, หัวข้อ 29 |
| Peripheral / core state | ไม่อยู่ในตารางสิทธิ์แฟลช; ตรวจแต่รีจิสเตอร์ที่มีคำอธิบายการอ่านชัดเจน การอ่านสำเร็จของรีจิสเตอร์หนึ่งไม่รับรองทุกช่วง address | 644-648, หัวข้อ 28 |
| เปลี่ยน L1 เป็น L0 | ลบ main flash อัตโนมัติ จึงไม่ใช่ทางสำรองเฟิร์มแวร์เดิม | 15, 2.2.1.9 |

คู่มือหน้า 15 จำกัดการอ่านแฟลชตามปกติไว้ที่การเริ่มจาก main flash ในสถานะไม่ใช่ debugging. หน้า 16 ห้ามการอ่านจากโปรแกรมที่เริ่มจาก SRAM รวมถึง DMA. ตารางแยก **สถานที่บูต** และ **ผู้เข้าถึง**: เมื่อบูต main flash คอลัมน์ CPU/SRAM ต่างจากกรณีบูต SRAM. จึงไม่ควรตีความว่าคำสั่งใดที่อยู่ใน SRAM จะถูกห้ามเสมอ หรือว่าคอลัมน์ CPU อนุญาตให้ debugger อ่านแฟลชได้

หัวข้อ debug หน้า 644 อธิบายการหยุดและทำงานต่อโดยทั่วไป แต่ไม่ได้รับรองว่าเพียงเปิด SWD/DP โดยไม่สั่ง halt จะคงการทำงานของแอปที่เปิด L1 ทุกกรณี. ต้องแยกหลักฐาน `CPUID`/DP ติดต่อได้ ออกจากหลักฐาน CPU กำลังทำงาน และจากหลักฐานแอปเดิมกำลังทำงานตามปกติ. ไม่มีการรับรองเส้นทางอ่านแฟลชทั้งหมดโดยไม่ลบผ่าน SWD, DMA หรือโปรแกรมบูตจาก SRAM ในส่วนที่ตรวจ

## ตำแหน่งอ่านที่ยืนยันแล้ว

| Address / ขนาด | ความหมาย | หน้า |
|---|---|---|
| `0x4002201C`, 4 bytes / word | `FLASH_OB`: bit 31 = L2, bit 1 = L1, bit 0 = option-byte complement error | 9, 29 |
| `0xE0042000`, 4 bytes / word เท่านั้น | `DBG_ID`: bits 27:24 ระบุ series (`1=G`, `2=L`); model = `((id >> 4) & 0xFF0) \| ((id >> 20) & 0xF)`; flash = bits 19:16 × 32 KiB; SRAM = (bits 31:28 + 1) × 8 KiB | 647-648 |
| `0x1FFFF800`, 4 bytes / word | byte ต่ำสุด = RDP1, byte ถัดไป = complement | 13 |
| `0x1FFFF810`, 4 bytes / word | byte ต่ำสุด = RDP2, byte ถัดไป = complement | 13 |

## สิ่งที่อ่านได้จากเครื่องจริง

ค่าต่อไปนี้เป็นผลที่ผู้ตรวจเครื่องหลักส่งให้เมื่อ 2026-09-20; ผู้จัดทำเอกสารนี้ไม่ได้สั่งอ่านอุปกรณ์เอง. ณ ชุดข้อมูลนี้ยังไม่มีคำสั่ง halt, reset, เขียน target memory หรือเปลี่ยน option bytes

| ผลที่รายงาน | ข้อสรุปที่รองรับ |
|---|---|
| ST-Link `V2J31M7`, VTref ประมาณ 3.15 V, DPIDR `0x2BA01477`, CPUID `0x410FC241` | ติดต่อ debug port และอ่านรหัส core ได้; CPUID อย่างเดียวไม่ยืนยันยี่ห้อ/รุ่น |
| `DBG_ID=0x22644017` | ตามแผนผังหน้า 647-648: N32L406, SRAM 24 KiB, flash 128 KiB, revision `0x17`; ผู้ใช้แจ้งว่าตัวอักษรบนชิปถูกลบ จึงยังไม่ทราบ package จากฉลาก |
| `FLASH_OB=0x03FFFFFE` | L1 เปิด, L2 ปิด, OBERR ไม่ขึ้น |
| `0x1FFFF800=0x00FFFF00`; `0x1FFFF810=0xFFFFFFFF` | RDP1/complement = `00/FF`; RDP2/complement = `FF/FF`; ตามตาราง 2-5 หน้า 15 เป็น L1 ไม่ใช่ค่าเปิด L0 หรือ L2 |
| อ่าน `0x08000000`, `0x08006800`, `0x0801F000` เกิด transfer fault | สอดคล้องกับการห้ามอ่าน main flash ผ่าน SWD ที่ L1; ไม่ใช่หลักฐานว่า flash ว่างหรือไฟล์เสีย |
| `VTOR=0x08006800` | vector table ชี้ฐานแอปที่คาดไว้ แต่ไม่ยืนยันว่าเป็น PN1.13 หรือไฟล์ใด |
| อ่าน SRAM ได้ครบ 24 KiB; ผู้ตรวจรายงานประมาณ 16 KiB เป็นข้อมูลไม่เป็นศูนย์ | เก็บสภาพ RAM ได้จริง; ไม่ใช่ backup main flash และยังไม่ยืนยันว่า CPU กำลังรันตามปกติ |

ผลติดตามอ่าน `DHCSR=0x01010000` ซ้ำ: CPU มี instruction retirement, ไม่ halt/lockup,
และ C_DEBUGEN=0. เมื่อผู้ใช้เปิดด้วยแบตก่อนแล้วต่อ GND/SWCLK/SWDIO โดยไม่มีไฟจาก
ST-Link ตัวจับเวลาและข้อมูล RAM เดินตามปกติ ดู [ผลตรวจสด](RX-SWD-FINDINGS-2026-09-20.md).
การยืนยันว่าเฟิร์มแวร์ candidate ทำงานจริงยังต้องใช้หลักฐานเพิ่มเติม

## งานที่เดินหน้าต่อได้โดยไม่ลบข้อมูล

1. วิเคราะห์ไฟล์ stock/vendor และเฟิร์มแวร์ในโครงการ พร้อมเทียบข้อมูลตัวตนและสถานะจากเครื่องจริง
2. เก็บ SRAM/core/status ที่อ่านได้โดยไม่สั่งเขียนโปรแกรม; ข้อมูลเหล่านี้ไม่ใช่สำเนา main flash และภาพ SRAM ที่อ่านขณะ CPU ทำงานอาจเปลี่ยนระหว่างการอ่าน
3. ตรวจพฤติกรรม bootloader เดิมและกระบวนการ update ที่ผู้ผลิตรับรอง. สิทธิ์ IAP ของ CPU ในคู่มือไม่ใช่หลักฐานว่า FNIRSI bootloader มีคำสั่ง readback หรือจะยอมรับไฟล์ใด; งานนี้ไม่พบหลักฐานใหม่เรื่องชื่อไฟล์/เงื่อนไขรับไฟล์ RX จึงไม่เพิ่มข้อสรุปดังกล่าว

การอ่านด้วยเครื่องมืออีกยี่ห้อไม่เปลี่ยนสิทธิ์ L1. การปลดล็อก, mass erase, เปลี่ยน option bytes หรือโหลดโปรแกรมเข้า SRAM ไม่อยู่ในขั้นตอนตรวจแบบรักษาข้อมูลนี้. ผลที่ยังขาดคือสำเนา main flash ที่อ่านตรวจสอบได้ หรือหลักฐานรับเฟิร์มแวร์จาก bootloader ที่ชัดเจน; ต้องไม่อ้างว่าได้ reverse engineer bootloader ของเครื่องจริงครบแล้ว

## ตรวจเพิ่ม: เขียนเฉพาะแอป, ROM CRC และงานวิจัยตรงรุ่น

**SWD ไม่ได้มีสิทธิ์เขียนเฉพาะแอปโดยอัตโนมัติเมื่อเปิด L1.** ตาราง 2-6 หน้า 16, 18, 19 ใช้คอลัมน์ JTAG/SWD แยกจากคอลัมน์ผู้เข้าถึงที่เป็นโค้ด CPU; ในคอลัมน์ JTAG/SWD แถว main flash ถูกห้าม ส่วน mass erase มีแถวอนุญาตแยกต่างหาก. หน้า 15 ยังระบุว่าการเขียน/ลบทุก page ใน debug mode ถูกห้าม ยกเว้น mass erase. สิทธิ์ IAP ของโปรแกรมที่รันอยู่ในแฟลชจึงไม่ใช่หลักฐานว่าการใช้ ST-Link เขียนช่วงแอปจะรักษา bootloader ได้

อ้างอิงเพิ่ม: [Nations BOOT interface instruction user guide V2.0](https://nsing.com.sg/api/dowfilebefore?did=4989), เอกสาร EN ภายใน ZIP, SHA-256 ของ PDF `687d69d1b5fe507d680e797c97fcd8b7f11fc6b8e27665bbe22ab2ee94ed6955`. หน้าในเนื้อหา + 2 = หน้า PDF; ตรวจภาพหน้า PDF 17-18 แล้ว

| ประเด็น ROM BOOT | ข้อเท็จจริงจากคู่มือ |
|---|---|
| `CMD_DATA_CRC_CHECK`, หัวข้อ 2.2.7 หน้า 15-16 | Host ส่ง CRC32 ที่คาดไว้, address และ length; ชิปส่งสถานะผ่าน/ไม่ผ่าน โดยไม่มี data payload. ไม่ใช่คำสั่งส่ง CRC ที่คำนวณได้หรือส่งเนื้อหาแฟลชกลับมา |
| ข้อจำกัด CRC | ตรวจ authentication หากเปิดใช้, ขอบเขต partition, address และการจัดแนว 16 bytes. ระบุขั้นต่ำระดับ 2 KiB โดยข้อความหน้า 15/16 ใช้ถ้อยคำ `minimum` และ `larger than` ต่างกัน จึงยังไม่ยืนยันขอบเขตเท่ากับ 2 KiB |
| RDP กับ CRC | รายการข้อผิดพลาด CRC ไม่ระบุ RDP โดยตรง; รายการ RDP error `B0/30` หน้า 22 ระบุ erase/download. การไม่มีรายการนี้ไม่รับรองว่า CRC ใช้ได้ใน L1 ทุกกรณี และไม่ใช่หลักฐานว่า L1 ห้าม CRC เสมอ |
| สิ่งที่อาจได้ | หากเข้า ROM BOOT และผ่านเงื่อนไขได้ อาจเทียบกับ CRC ของไฟล์ที่มีอยู่แล้ว; ความพร้อมบน RX จริงยังไม่ยืนยัน และช่องทางนี้แยกจาก UDISK ของ FNIRSI |

การค้นแบบจำกัดเมื่อ 2026-09-20 ใช้ชื่อ `N32L40x`, `N32L406` กับคำอังกฤษ/จีนเกี่ยวกับ readout bypass, debug bypass, fault injection, CVE และอ่านป้องกัน รวมทั้งค้นเจาะ IACR/NVD. **ยังไม่พบงานวิจัยต้นทางหรือประกาศช่องโหว่ตรงรุ่นที่สาธิตการอ่านแฟลชเดิมโดยไม่ลบด้วย ST-Link หรือวิธีอื่น**. นี่คือขอบเขตของผลค้น ไม่ใช่ข้อพิสูจน์ว่าไม่มีช่องโหว่. ไม่ได้นำวิธีของ STM32/GD32 หรือคำโฆษณารับถอดรหัสมาอ้างว่าใช้กับ N32L406 ได้

ด้วยอุปกรณ์ปัจจุบัน งานที่มีหลักฐานรองรับยังเป็นการอ่านสถานะ/RAM ที่เข้าถึงได้และการวิเคราะห์ไฟล์ที่มีอยู่. วิธี fault injection, decapsulation หรือการวัดเฉพาะทางยังไม่มีขั้นตอนตรงรุ่นที่ยืนยันจากหลักฐานข้างต้น และไม่มีเหตุให้รับรองผลเพียงซื้ออุปกรณ์เพิ่ม. การตรวจนี้ไม่ส่งคำสั่ง CRC, ไม่เปลี่ยนโหมดบูต และไม่ทดลอง bypass
